## 問題描述

OpenBMC 的最終使用者可能會執行一些會改變系統狀態及（或）設定的動作。這些動作可以透過 OpenBMC 所提供的眾多介面來執行，包括 RedFish、IPMI、ssh 或序列主控台 shell，以及其他介面，也包含未來新增的介面。

這些動作的後果有時可能造成危害，因此可能需要進行調查，以找出該為不受歡迎的變更負責的人。目前，大多數變更不會在 OpenBMC 記錄中留下任何痕跡，這讓上述調查難以進行。

因此需要開發一種機制，能夠追蹤這類使用者活動、記錄它們，並在必要時採取某些動作。

## 背景與參考

YADRO 內部曾有一套針對此問題的解決方案。它僅適用於舊版的 OpenBMC，需要重新設計。此外，IBM 也有一項平行的工作，可在此處找到：
[REST and Redfish Traffic Logging](https://gerrit.openbmc.org/c/openbmc/bmcweb/+/22699)

## 假設

本設計假設最終使用者絕不會被直接賦予系統 shell 的存取權。shell 允許直接操作使用者資料庫（新增／移除使用者、變更密碼）與系統設定（網路腳本等等），因此要追蹤在 shell 內執行的這類使用者動作似乎並不可行。本設計假設所有使用者與 OpenBMC 的互動，都受限於由其他 Phosphor OpenBMC 元件透過 D-Bus 互動所提供、受控管的介面。

## 需求

- 盡可能提供一種獨立於使用者介面的統一使用者動作記錄方式，可能的使用者動作包括：
  - Redfish/REST PUT/POST/DELETE/PATCH
  - IPMI
  - PAM
  - PLDM
  - 其他任何適合的服務
- 提供一種方式，可設定針對某些使用者動作所採取的系統回應動作，可能的回應動作包括：
  - 記錄一個事件
  - 通知管理員或任意通知接收者
  - 執行任意指令
- 提供一種方式來設定通知接收者：
  - 電子郵件
  - SNMP
  - 即時通訊軟體
  - D-Bus

## 建議設計

主要概念是攔截由使用者介面送出的 D-Bus 請求，接著依照設定來處理該請求。未來可以實作彈性化的政策，讓處理與追蹤更具彈性。

phosphor-audit 服務是一項提供使用者活動追蹤、並針對使用者動作採取對應回應動作的服務。

使用 phosphor-audit 的主要好處是，所有的動作處理都會集中保留在這個專案內，而不會分散到多個專屬介面服務中，避免其中某個服務可能漏掉某個動作的處理常式、以及讓程式碼庫膨脹的風險。

下方的元件圖顯示一個服務總覽範例。

```ascii
  +----------------+  audit event                           +-----------------+
  |    IPMI NET    +-----------+                            | action          |
  +----------------+           |                            | +-------------+ |
                               |                            | |   logging   | |
  +----------------+           |                            | +-------------+ |
  |   IPMI HOST    +-----------+      +--------------+      |                 |
  +----------------+           |      |    audit     |      | +-------------+ |
                               +----->+   service    +----->| |   command   | |
  +----------------+           |      |              |      | +-------------+ |
  |  RedFish/REST  +-----------+      +--------------+      |                 |
  +----------------+           |                            | +-------------+ |
                               |                            | |   notify    | |
  +----------------+           |                            | +-------------+ |
  |  any service   +-----------+                            |                 |
  +----------------+                                        | +-------------+ |
                                                            | |     ...     | |
                                                            | +-------------+ |
                                                            +-----------------+
```

圖中的稽核事件由應用程式產生，用以追蹤使用者活動。應用程式透過 D-Bus 送出一個「signal」給稽核服務。接下來在稽核服務的處理常式中會發生什麼事，取決於使用者的需求與需要。在處理常式中，可以只儲存記錄、執行任意指令或通知某人，也可以同時做以上全部，而且這一切都可選擇性啟用。

### 稽核事件呼叫

稽核事件呼叫會在應用程式端先對傳入資料進行前置處理，再送往稽核服務；如果請求被篩除，就會在此時被丟棄，不再進一步處理。通過篩檢檢查後，稽核事件呼叫會透過 D-Bus 將資料送到稽核服務，由稽核服務決定後續步驟。此外，它會快取可能的指令清單（黑名單或白名單）以及其服務狀態（停用或啟用）。若服務處於未定義狀態，此呼叫會檢查服務是否存活。

> `audit_event(type, rc, request, user, host, data)`
>
> - type - 事件來源的類型：IPMI、REST、PAM 等。
> - rc - 處理常式事件的回傳碼（status、rc 等）。
> - request - 事件的通用識別碼，例如 ipmi 指令
>   （cmd/netfn/lun）、web 路徑，或任何可用來描述該事件的資訊。
> - user - 該事件是代表哪個使用者帳戶處理的。依情境而定，當使用者無法取得時為 NA/None。
> - source - 該事件來源主機的識別碼。對於來自本機主機的（透過本機連接的 IPMI）事件，它可以確實是 "host"，或是遠端主機的 IP 位址或主機名稱。
> - data - 任何可協助更好辨識該事件的輔助資料（例如，IPMI 指令資料的某些前幾個位元組）。

服務本身可以透過其自身端的設定來控制事件的流向。

範例偽碼：

```cpp
    audit_event(NET_IPMI, "access denied"(rc=-1), "ipmi cmd", "qwerty223",
                          "192.168.0.1", <some additional data if needed>)
    audit_event(REST, "login successful"(rc=200), "rest login",
                      "qwerty223", "192.168.0.1", NULL)
    audit_event(HOST_IPMI, "shutting down the host"(rc=0), "host poweroff",
                       NULL, NULL, NULL)
```

`audit_event(blob_data)` Blob 可以描述為以下結構：

```cpp
    struct blob_audit
    {
        uint8_t type;
        int32_t rc;
        uint32_t request_id;
        char *user;
        sockaddr_in6 *addr;
        struct iovec *data;
    }
```

當此呼叫透過 D-Bus 抵達伺服器端目的地時，伺服器已經知道該呼叫應透過在伺服器設定中預先定義的動作清單來處理。

呼叫的逐步執行流程：

- 客戶端層
  1. 檢查此服務是否已啟用稽核
  2. 檢查在稽核服務端是否應將該稽核事件列入白名單或黑名單，以防止不必要的事件氾濫稽核服務
  3. 透過 D-Bus 將資料送至稽核服務
- 伺服器端層
  1. 接受 D-Bus 請求
  2. 針對每個服務逐一檢視動作清單

在客戶端層如何進行這些檢查：

1. 檢查服務狀態並快取該值
2. 檢查應被記錄的可能動作清單並同時快取它們
3. 監聽 'propertiesChanged' 事件，以防清單或服務狀態發生變更

## 服務設定

設定結構可以描述為一棵帶有各種選項的樹，結構範例如下：

```text
[IPMI]
   [Enabled]
   [Whitelist]
     [Cmd 0x01] ["reset request"]
     [Cmd 0x02] ["hello world"]
     [Cmd 0x03] ["goodbye cruel world"]
   [Actions]
     [Notify type1] [Recipient]
     [Notify type2] [Recipient]
     [Notify type3] [Recipient]
     [Logging type] [Options]
     [Exec] [ExternalCommand]
[REST]
   [Disabled]
   [Blacklist]
     [Path1] [Options]
     [Path2] [Options]
   [Actions]
     [Notify type2] [Recipient]
     [Logging type] [Options]
```

選項可以透過 D-Bus 屬性來更新。稽核服務會監聽設定檔的變更，並發出帶有變更詳細資訊的 'PropertiesChanged' signal。

- 白名單與黑名單

> 可能被篩檢並處理的請求清單。'Whitelist' 會篩出可被處理的請求。'Blacklist' 只封鎖確切的請求。

- 針對指定服務啟用／停用事件處理，這裡的指定服務是指任何可使用稽核服務的適合服務。

> 每種稽核處理類型都可以在執行期間透過設定檔或 D-Bus 屬性來停用或啟用。

- 透過 SNMP／電子郵件／即時通訊軟體／D-Bus 進行通知設定

> 具備不同傳輸方式的最終接收者通知系統。

- 記錄

> phosphor-logging、journald 或其他任何適合的方式。

- 使用者動作

> 作為後續動作執行一道指令。

## 通知機制

一種向最終使用者回報事故之統一模型，其傳輸方式可以是：

- 電子郵件

  > 透過 sendmail 或其他任何方式，寄送通知給在設定中指定的接收者。

- SNMP

  > 透過 SNMP trap 訊息，寄送通知給在設定中指定的接收者。

- 即時通訊軟體

  > 透過 jabber/sametime/gtalk/等，寄送通知給在設定中指定的接收者。

- D-Bus

  > 透過 'method_call' 或 'signal'，通知在設定中指定的其他服務。

若設定之中未設定上述任何規則，通知將被跳過。可以在執行期間擷取規則。

## 使用者動作

- 透過 'system' 呼叫執行應用程式。
- 在處理常式本身內部針對指定處理類型的程式碼。以 'net ipmi' 為例，當使用者登入失敗時，在處理常式中：
  - 發送通知給管理員。
  - echo heartbeat > /sys/class/leds/alarm_red/trigger

## 曾考慮的替代方案

在每個專屬介面服務中處理使用者請求，並針對每個介面分別記錄它們。分散式的處理看起來是一種容易出錯且僵化的做法。

## 影響

改善系統的可管理性與安全性。

當 phosphor-audit 未啟用時的影響：

- 由於會呼叫 audit_event()，許多服務的程式碼大小會略微增加、CPU 路徑長度也會變長。
- D-Bus 流量增加。

當 phosphor-audit 啟用時的影響：包含上述全部，另外還有：

- 處理稽核事件需要額外的 BMC 處理器時間。
- 儲存已記錄事件需要額外的 BMC 快閃儲存空間。
- 通知使用者會產生額外的對外網路流量。
- 通知函式庫需要額外空間。

## 測試

`dbus-send` 作為產生稽核事件的命令列工具。

情境：

- 針對每個受支援的服務（例如 Redfish、net IPMI、host IPMI、PLDM）建立稽核事件，並驗證它們會被記錄。
- 確保訊息類型與請求類型的篩檢如預期運作。
- 確保基本的通知動作如預期運作（記錄、指令、通知）。
- 在持續產生稽核事件的同時，變更 phosphor-audit 服務的設定，並驗證不會遺失任何稽核事件，且新設定會生效。
